Foreign Data Wrapper для Oracle
===============================

[English](README.md) | **Русский**

oracle_fdw — это расширение PostgreSQL, предоставляющее обёртку сторонних
данных (foreign data wrapper) для простого и эффективного доступа к базам
данных Oracle, включая проталкивание условий WHERE и нужных столбцов,
а также всестороннюю поддержку EXPLAIN.

> **Об этом форке:** этот репозиторий — форк
> [laurenz/oracle_fdw](https://github.com/laurenz/oracle_fdw), созданный для
> миграции на PostgreSQL кода Oracle, использующего database link и вызовы
> удалённых функций и пакетов PL/SQL.  В отличие от оригинала, он содержит
> функции `oracle_query`, `oracle_scalar`, `oracle_call` и `oracle_exec`
> (ветка `feature/oracle-query`), которые позволяют выполнять запросы и
> вызывать удалённые функции, процедуры и анонимные блоки PL/SQL на сервере
> Oracle из PostgreSQL; см. разделы
> [Объекты, создаваемые расширением](#2-объекты-создаваемые-расширением) и
> [Использование](#4-использование).  Всё остальное — исходный код оригинала
> без изменений; форк синхронизируется с оригиналом слияниями.

1 Быстрый старт
===============

Это простой пример использования oracle_fdw.  
Более подробные сведения приведены в разделах [Параметры](#3-параметры) и
[Использование](#4-использование).  Также стоит прочитать
[документацию PostgreSQL по внешним данным][fd] и описание упомянутых там
команд.

 [fd]: https://www.postgresql.org/docs/current/static/ddl-foreign-data.html

Для примера предположим, что вы можете подключиться от имени пользователя
операционной системы `postgres` (или того, кто запускает сервер PostgreSQL)
следующей командой:

    sqlplus orauser/orapwd@//dbserver.mydomain.com:1521/ORADB

Это означает, что клиент Oracle и окружение настроены правильно.
Также предположим, что oracle_fdw уже скомпилирован и установлен
(см. раздел [Установка](#6-установка)).

Пусть мы хотим обратиться к таблице, определённой так:

    SQL> DESCRIBE oratab
     Name                            Null?    Type
     ------------------------------- -------- ------------
     ID                              NOT NULL NUMBER(5)
     TEXT                                     VARCHAR2(30)
     FLOATING                        NOT NULL NUMBER(7,2)


Затем настройте oracle_fdw от имени суперпользователя PostgreSQL так:

    pgdb=# CREATE EXTENSION oracle_fdw;
    pgdb=# CREATE SERVER oradb FOREIGN DATA WRAPPER oracle_fdw
              OPTIONS (dbserver '//dbserver.mydomain.com:1521/ORADB');

(Можно использовать другие способы именования или локальные подключения,
см. описание параметра **dbserver** ниже.)

Хорошая практика — использовать суперпользователя только там, где это
действительно необходимо, поэтому разрешим обычному пользователю работать
с внешним сервером (для работы примера это не требуется, но я рекомендую
так делать):

    pgdb=# GRANT USAGE ON FOREIGN SERVER oradb TO pguser;

Затем подключитесь к PostgreSQL как `pguser` и определите:

    pgdb=> CREATE USER MAPPING FOR pguser SERVER oradb
              OPTIONS (user 'orauser', password 'orapwd');

(Чтобы не хранить учётные данные Oracle в PostgreSQL, можно использовать
внешнюю аутентификацию; см. ниже.)

    pgdb=> CREATE FOREIGN TABLE oratab (
              id        integer           OPTIONS (key 'true')  NOT NULL,
              text      character varying(30),
              floating  double precision  NOT NULL
           ) SERVER oradb OPTIONS (schema 'ORAUSER', table 'ORATAB');

(Помните, что имя таблицы и схемы — последнее необязательно — как правило,
должно быть записано в верхнем регистре.)

Теперь с таблицей можно работать как с обычной таблицей PostgreSQL.

2 Объекты, создаваемые расширением
==================================

    FUNCTION oracle_fdw_handler() RETURNS fdw_handler
    FUNCTION oracle_fdw_validator(text[], oid) RETURNS void

Это функции-обработчик и функция-валидатор, необходимые для создания
обёртки сторонних данных.

    FOREIGN DATA WRAPPER oracle_fdw
      HANDLER oracle_fdw_handler
      VALIDATOR oracle_fdw_validator

Расширение автоматически создаёт обёртку сторонних данных с именем
`oracle_fdw`.  
Обычно этого достаточно, и можно переходить к определению внешних серверов.
Дополнительные обёртки Oracle можно создать, например, если нужно задать
параметр **nls_lang** (можно изменить и существующую обёртку `oracle_fdw`,
но все изменения будут потеряны после дампа/восстановления).

    FUNCTION oracle_close_connections() RETURNS void

Эта функция позволяет закрыть все открытые подключения Oracle в текущем
сеансе.  Подробнее см. раздел [Использование](#4-использование).

    FUNCTION oracle_diag(name DEFAULT NULL) RETURNS text

Эта функция предназначена только для диагностики.  
Она возвращает версии oracle_fdw, сервера PostgreSQL и клиента Oracle.
При вызове без аргумента или с NULL она дополнительно возвращает значения
некоторых переменных окружения, используемых для установки подключений
к Oracle.  
При вызове с именем внешнего сервера дополнительно возвращается версия
сервера Oracle.

    FUNCTION oracle_execute(server name, stmt text) RETURNS void

Эта функция позволяет выполнять произвольные операторы SQL на удалённом
сервере Oracle.  Работает только с операторами, которые не возвращают
результат (обычно это операторы DDL).

Пользуйтесь этой функцией осторожно: она может нарушить управление
транзакциями в oracle_fdw.  Помните, что выполнение DDL в Oracle вызывает
неявный COMMIT.
Лучше всего использовать эту функцию вне многооператорных транзакций.

    FUNCTION oracle_query(server name, stmt text, params text[] DEFAULT NULL)
           RETURNS SETOF record
    FUNCTION oracle_scalar(server name, stmt text, params text[] DEFAULT NULL)
           RETURNS text

Эти функции позволяют выполнить на удалённом сервере Oracle запрос,
возвращающий результат — как правило, для вызова удалённой функции или
функции пакета, которую в Oracle иначе вызывают через database link.

Обе функции принимают одни и те же три аргумента:

- имя внешнего сервера;
- выполняемый оператор;
- необязательный массив строк, привязываемый к параметрам связывания
  `:1`, `:2`, ... в операторе (элемент массива со значением NULL привязывает
  SQL NULL; значения передаются как строки и интерпретируются Oracle,
  поэтому `ARRAY['50']` — допустимое значение для параметра типа `NUMBER`).

Обе функции требуют, чтобы оператор был именно запросом; что считать
запросом, решает Oracle, поэтому ключевые слова в нижнем регистре, начальные
пробелы и комментарии допустимы, а DML, DDL и блоки PL/SQL отвергаются
с ошибкой.  Операторы без результата выполняйте с помощью `oracle_execute`,
а функции, изменяющие данные, — с помощью `oracle_call` (см. ниже).

Функции различаются тем, как возвращается результат:

- Используйте **oracle_query**, если оператор возвращает *набор строк*
  (любое число строк и столбцов).  Она возвращает все строки результата,
  и вам нужно объявить типы результата в списке определений столбцов в
  месте вызова.  Типичные сценарии — чтение данных с удалённого сервера и
  «массовый» вызов удалённых функций, вычисляющих результаты сразу для
  многих строк.

- Используйте **oracle_scalar**, если оператор возвращает *одно значение*.
  Она возвращает первый столбец первой строки результата как `text`
  (NULL, если оператор не вернул строк или первое значение NULL).  Читается
  только первый столбец, а выборка останавливается после первой строки,
  поэтому последующие строки и столбцы не передаются и не вычисляются;
  ошибка или неподдерживаемый тип данных там не повлияют на вызов.
  Типичные сценарии — вызовы удалённых функций в присваиваниях и в
  условиях, то есть именно то, что делают вызовы через Oracle database link
  вида `pkg.func@dblink(...)`.

    FUNCTION oracle_call(server name, func text, VARIADIC args text[] DEFAULT NULL)
           RETURNS text
    FUNCTION oracle_exec(server name, block text, VARIADIC args text[] DEFAULT NULL)
           RETURNS text

Эти функции позволяют вызывать удалённые функции, изменяющие данные, и
удалённые процедуры с OUT-параметрами, чего не может сделать запрос;
см. разделы о **oracle_call** и **oracle_exec** ниже.

`oracle_query`, `oracle_scalar`, `oracle_call` и `oracle_exec` лишаются
права `PUBLIC` при создании расширения, поскольку они могут выполнять
произвольный SQL на сервере Oracle с учётными данными из сопоставления
пользователя вызывающего.  Выдайте на них `EXECUTE` ролям, которым это
нужно:

    GRANT EXECUTE ON FUNCTION oracle_query(name, text, text[]) TO migrator;
    GRANT EXECUTE ON FUNCTION oracle_scalar(name, text, text[]) TO migrator;
    GRANT EXECUTE ON FUNCTION oracle_call(name, text, text[]) TO migrator;
    GRANT EXECUTE ON FUNCTION oracle_exec(name, text, text[]) TO migrator;

`oracle_execute` сохраняет право `PUBLIC` по умолчанию ради обратной
совместимости с существующими установками.

**Почему функций четыре**

Четыре функции покрывают два независимых выбора: форму результата и
контекст, в котором Oracle выполняет оператор.

| Результат          | Query-контекст      | PL/SQL-контекст         |
|--------------------|---------------------|-------------------------|
| Набор строк        | `oracle_query`      | —                       |
| Одно значение      | `oracle_scalar`     | `oracle_call`, `oracle_exec` |

Query-контекст — это обычный SQL-контекст: Oracle сам решает, является ли
оператор запросом, и отвергает DML с `ORA-14551`.  PL/SQL-контекст
выполняет анонимный блок, поэтому может вызывать функции, изменяющие
данные, и процедуры с OUT-параметрами.

Внутри есть только две реализации.  `oracle_query` и `oracle_scalar`
используют общий код динамических запросов, а `oracle_call` и `oracle_exec`
— общий код анонимного блока.  Публичных функций четыре, потому что у них
разные контракты:

- `oracle_query` — единственная функция, возвращающая набор строк и
  столбцов.  Так как типы результата неизвестны при определении функции,
  в месте вызова нужен список определений столбцов.
- `oracle_scalar` возвращает одно значение как `text` без списка
  определений столбцов и останавливается после первой строки и первого
  столбца.  Это не эквивалент `oracle_query ... LIMIT 1`: `LIMIT` не
  останавливает удалённую вычитку, потому что PostgreSQL сначала
  материализует весь результат (см. **LIMIT и материализация результата**),
  а `oracle_scalar` вдобавок не описывает последующие столбцы.
- `oracle_call` — удобная проверяемая форма для функции с простым именем.
  Она собирает блок `BEGIN :p0 := func(:p1, ...); END;` и проверяет имя
  функции.
- `oracle_exec` — общая форма для процедур с OUT-параметрами, имён в
  кавычках или перегруженных имён и произвольных блоков PL/SQL.  Блок
  принимается как есть, проверяются только bind-параметры.

`oracle_call` — удобная обёртка над тем же механизмом, что и `oracle_exec`.
`oracle_exec` нельзя убрать без потери процедур с OUT-параметрами и
произвольных блоков, а `oracle_call` можно было бы заменить ручным
написанием блока.  Наличие обеих функций делает обычный вызов функции
коротким и безопасным и при этом оставляет общий «аварийный выход».

Правило выбора:

1. Оператор возвращает много строк или столбцов: `oracle_query`.
2. Оператор возвращает одно значение и не изменяет данные:
   `oracle_scalar`.
3. Нужно вызвать функцию с простым именем, которая может изменять данные:
   `oracle_call`.
4. Нужно вызвать процедуру с OUT-параметрами, имя в кавычках или
   перегруженную функцию, либо выполнить произвольный блок PL/SQL:
   `oracle_exec`.

**oracle_query подробно**

Поскольку типы результата нельзя определить при определении функции,
в месте вызова нужно указать список определений столбцов:

    SELECT * FROM oracle_query('oradb', 'SELECT * FROM all_users')
        AS q(username text, user_id numeric);

Параметризованный оператор, читающий данные, соответствующие условию:

    SELECT * FROM oracle_query(
               'oradb',
               'SELECT first_name FROM employees WHERE department_id = :1',
               ARRAY[50::text]) AS q(first_name text);

«Массовый» вызов удалённой функции: вместо вызова функции для каждой строки
в PostgreSQL (по одному сетевому обмену на вызов) все результаты
вычисляются одним оператором на сервере Oracle:

    SELECT * FROM oracle_query('oradb',
               'SELECT e.ename, scott.calc_bonus(e.ename, e.hiredate, e.job)
                FROM emp e WHERE e.hiredate >= :1',
               ARRAY[to_char(current_date, 'YYYY-MM-DD HH24:MI:SS')])
        AS q(ename text, bonus numeric);

Учтите, что параметр связывания типа DATE должен передаваться в формате
`NLS_DATE_FORMAT` сеанса oracle_fdw, то есть `YYYY-MM-DD HH24:MI:SS`;
для другого формата преобразуйте значение на удалённой стороне, например
с помощью `TO_DATE(:1, 'YYYY-MM-DD')`.

Значения результата Oracle преобразует в строки согласно настройкам NLS
сеанса, а затем они преобразуются в типы PostgreSQL из списка определений
столбцов функциями ввода этих типов.
В списке выборки поддерживаются только типы с осмысленным строковым
представлением (CHAR/VARCHAR2, NUMBER, FLOAT, BINARY_FLOAT, BINARY_DOUBLE,
DATE, TIMESTAMP, INTERVAL и RAW); остальные типы (LOB, LONG и
пользовательские типы) преобразуйте явно с помощью CAST или TO_CHAR.
Столбец RAW передаётся как шестнадцатеричная строка: объявите столбец
результата как `text`, чтобы получить шестнадцатеричное представление,
или как `bytea`, чтобы получить двоичное значение.

Параметры связывания в операторе позиционные: `:1`, `:2`, ...; они должны
идти подряд, и один и тот же параметр может повторяться.  Параметры внутри
обычных строковых литералов, идентификаторов в кавычках, комментариев и
q-строк (`q'...'` и `nq'...'`) не привязываются.  Именованные параметры
вида `:name` отвергаются с ошибкой, а число параметров сверяется с числом
bind-переменных, которое сообщает Oracle, ещё до выполнения оператора.

**LIMIT и материализация результата**

`oracle_query` — это set-returning функция с вызовом на строку
(value-per-call SRF).  Исполнитель PostgreSQL вызывает её многократно и
сохраняет все возвращённые строки в tuplestore до того, как вычисляется
внешний запрос, включая `LIMIT` и `OFFSET`.  Tuplestore может выгружаться
на диск, поэтому память PostgreSQL остаётся ограниченной, но весь результат
всё равно вычитывается из Oracle и преобразуется в значения PostgreSQL.

Следовательно, `LIMIT` ограничивает только число строк, возвращаемых
внешним запросом; он не уменьшает число строк, читаемых из Oracle, сетевой
трафик и работу удалённого сервера.  Он также не предотвращает ошибки в
строках за пределами лимита.  Например, этот оператор всё равно завершится
ошибкой:

    SELECT * FROM oracle_query('oradb',
               'SELECT CASE WHEN level = 1 THEN 1 ELSE 1/0 END
                FROM dual CONNECT BY level <= 2') AS q(n numeric)
    LIMIT 1;

Ошибка будет `ORA-01476: divisor is equal to zero`, потому что PostgreSQL
материализует вторую строку до применения `LIMIT`.  По той же причине
`LIMIT` не закрывает удалённый курсор досрочно: курсор закрывается, когда
результат исчерпан, запрос отменён или произошла ошибка.

Если нужно ограничить работу на сервере Oracle, добавьте ограничение в
сам удалённый оператор, например `WHERE ROWNUM <= 10`,
`FETCH FIRST 10 ROWS ONLY` (Oracle 12c и новее) или обычное условие `WHERE`.
Такой оператор вернёт меньше строк, поэтому меньше строк будет передано и
материализовано.  У `oracle_scalar` этой проблемы нет: он определяет только
первый столбец и останавливается после первой строки.

**oracle_scalar подробно**

`oracle_scalar` возвращает первый столбец первой строки результата как
`text`, поэтому приводите результат к нужному типу.  В присваиваниях внутри
функций PL/pgSQL она заменяет присваивание через Oracle database link
`x := pkg.func@dblink(...)`:

    -- Oracle: empno := scott.get_empno@dblink('SCOTT')
    empno := oracle_scalar('oradb',
        'SELECT scott.get_empno(:1) FROM dual',
        ARRAY['SCOTT'])::numeric;

В предложении WHERE она заменяет вызов удалённой функции вида
`WHERE scott.calc_bonus@dblink(a, b, c) <> 0`; функция вызывается один раз
для каждой строки локальной таблицы, как и вызов через Oracle database link:

    SELECT * FROM emp e
    WHERE oracle_scalar('oradb',
          'SELECT scott.calc_bonus(:1, TO_DATE(:2, ''YYYY-MM-DD''), :3)
           FROM dual',
          ARRAY[e.ename, to_char(e.hiredate, 'YYYY-MM-DD'), e.job])::numeric
          <> 0;

Чтобы перенесённый код оставался читаемым, оборачивайте такие вызовы
в небольшие функции PostgreSQL с соответствующими типами аргументов
и результата; перенесённые операторы тогда выглядят почти как исходный код
Oracle:

    CREATE FUNCTION calc_bonus(ename text, hiredate date, job text)
       RETURNS numeric
       LANGUAGE sql
    AS $$
       SELECT oracle_scalar('oradb',
              'SELECT scott.calc_bonus(:1, TO_DATE(:2, ''YYYY-MM-DD''), :3)
               FROM dual',
              ARRAY[ename, to_char(hiredate, 'YYYY-MM-DD'), job])::numeric
    $$;

    SELECT * FROM emp e WHERE calc_bonus(e.ename, e.hiredate, e.job) <> 0;

Если вам нужно одно значение не типа `text`, либо приведите результат
к нужному типу, либо используйте `oracle_query` со списком определений
столбцов, которая даёт правильно типизированный результат:

    SELECT bonus FROM oracle_query('oradb',
           'SELECT scott.calc_bonus(:1, TO_DATE(:2, ''YYYY-MM-DD''), :3)
            FROM dual',
           ARRAY['SMITH', '1980-12-17', 'CLERK']) AS q(bonus numeric);

**oracle_call подробно**

`oracle_call` вызывает удалённую *функцию*, которая может изменять данные,
— этого не может сделать обычный запрос (Oracle отвергает DML в запросе
с ошибкой `ORA-14551`).  Функция вызывается через анонимный блок PL/SQL,
а результат функции возвращается через OUT-параметр связывания:

    SELECT oracle_call('oradb', 'scott.f_dml', 'x');
     oracle_call 
    -------------
               1

Имя функции должно состоять из одного-трёх сегментов-идентификаторов без
кавычек (`function`, `package.function` или `schema.package.function`),
каждый длиной не больше предела идентификаторов данной версии Oracle
(30 байт до Oracle 12.2, 128 байт начиная с неё).  Для имён в кавычках
и перегруженных функций нужен `oracle_exec`.

Аргументы привязываются как строками к позиционным параметрам связывания
`:p1`, `:p2`, ... (аргумент NULL привязывает SQL NULL); результат функции
возвращается как `text` (NULL, если функция вернула NULL).  Результат
может занимать не более 32767 байт — максимальной длины PL/SQL `VARCHAR2`;
более длинные результаты записывайте в таблицу или возвращайте CLOB
и читайте его с помощью `oracle_query` (результаты CLOB не поддерживаются).

DML, выполняемый функцией, участвует в локальной транзакции: он фиксируется
или откатывается вместе с транзакцией PostgreSQL, включая точки сохранения
и подтранзакции.  Это не относится к операциям со своими правилами
фиксации, например к автономным транзакциям и DDL.

**oracle_exec подробно**

`oracle_exec` выполняет анонимный блок PL/SQL, возвращающий результат.
Блок должен присвоить результат параметру связывания `:p0`, который
привязывается как OUT-параметр; аргументы привязываются как строки
к позиционным параметрам связывания `:p1`, `:p2`, ...:

    SELECT oracle_exec('oradb', 'BEGIN scott.p_out(:p1, :p0); END;', '7');
     oracle_exec 
    -------------
     v7

Используйте `oracle_exec` для процедур с OUT-параметрами и для функций,
которым нужны имена в кавычках.  Для блоков без результата используйте
`oracle_execute`; `oracle_exec` отвергает блок, не присваивающий `:p0`.

Блок должен присвоить результат `:p0`; остальные параметры должны идти по
порядку `:p1`, ..., `:pN`, и один и тот же параметр может повторяться.
Блок, не использующий `:p0`, отвергается с подсказкой использовать
`oracle_execute`; `:p00` считается другим, именованным параметром и
отвергается.  Число bind-переменных сверяется с числом, которое сообщает
Oracle.

Результат должен иметь длину не более 32767 байт; ограничения на
транзакции те же, что и для `oracle_call`.

**Общие ограничения**

Применяются те же ограничения, что и для `oracle_execute`: функции
выполняются с правами сопоставления текущего пользователя, а удалённые
операторы, изменяющие данные или имеющие другие побочные эффекты, не
участвуют в двухфазном управлении транзакциями oracle_fdw, поэтому
неявный COMMIT внутри вызванной функции PL/SQL нельзя откатить локальной
транзакцией.

См. раздел **LIMIT и материализация результата** выше: там описаны
потребление памяти, поведение `LIMIT` и время жизни курсора в
`oracle_query`.
Также учтите, что вызов `oracle_scalar` для каждой строки таблицы означает
по одному сетевому обмену на вызов; для массовой обработки эффективнее
выполнить один оператор с `oracle_query`, вычисляющий все результаты
сразу.

3 Параметры
===========

Параметры обёртки сторонних данных
----------------------------------

(Внимание: если вы измените обёртку сторонних данных по умолчанию
`oracle_fdw`, все изменения будут потеряны при дампе/восстановлении.
Если нужно, чтобы параметры сохранились, создайте новую обёртку.
Поставляемый с расширением SQL-скрипт содержит оператор
CREATE FOREIGN DATA WRAPPER, который можно использовать.)

- **nls_lang** (необязательный)

  Задаёт значение переменной окружения NLS_LANG для Oracle.  
  NLS_LANG имеет вид «language_territory.charset» (например,
  AMERICAN_AMERICA.AL32UTF8).  Значение должно соответствовать кодировке
  вашей базы данных.  Если этот параметр не задан, oracle_fdw автоматически
  сделает всё правильно, если сможет, и выдаст предупреждение, если нет.
  Задавайте его, только если понимаете, что делаете.
  См. раздел [Проблемы](#8-проблемы).

Параметры внешнего сервера
--------------------------

- **dbserver** (обязательный)

  Строка подключения к удалённой базе данных Oracle.  
  Подойдёт любая из поддерживаемых Oracle форм, если ваш клиент Oracle
  настроен соответствующим образом.  
  Для локальных подключений («BEQUEATH») задайте пустую строку.

- **isolation_level** (необязательный, по умолчанию `serializable`)

  Уровень изоляции транзакций для базы данных Oracle.  
  Значение может быть `serializable`, `read_committed` или `read_only`.
  (READ ONLY на самом деле является режимом доступа транзакции, а не
  уровнем изоляции, но здесь мы не будем вдаваться в это различие.)

  Заметьте, что к таблице Oracle в пределах одного оператора PostgreSQL
  может быть выполнено несколько обращений (например, при соединении
  вложенным циклом).  Чтобы исключить несогласованность из-за гонок
  с параллельными транзакциями, уровень изоляции транзакции должен
  гарантировать стабильность чтения.  
  Это гарантируют только уровни изоляции Oracle SERIALIZABLE и READ ONLY.

  К сожалению, реализация SERIALIZABLE в Oracle довольно плоха и вызывает
  ошибки сериализации (ORA-08177) в неожиданных ситуациях, например при
  вставке в таблицу.  
  Транзакции READ COMMITTED позволяют обойти эту проблему, но **есть риск
  несогласованности**.  Если хотите их использовать, проверяйте планы
  выполнения: не может ли внешнее сканирование выполняться более одного
  раза.

- **nchar** (boolean, необязательный, по умолчанию `off`)

  Значение `on` выбирает более дорогое преобразование символов на стороне
  Oracle.  Это требуется, если таблицы Oracle содержат столбцы NCHAR
  или NVARCHAR2 с символами, которые нельзя представить в кодировке базы
  данных Oracle.

  Установка `nchar` в `on` заметно снижает производительность и вызывает
  ошибки ORA-01461 в операторах UPDATE, задающих строки длиннее 2000 байт
  (или 16383 при MAX_STRING_SIZE = EXTENDED).
  Судя по всему, эта ошибка — баг Oracle.

- **set_timezone** (boolean, необязательный, по умолчанию `off`)

  Значение `on` устанавливает часовой пояс сеанса Oracle равным текущему
  значению параметра PostgreSQL `timezone` при установлении подключения
  к Oracle.  Это полезно, только если вы собираетесь использовать столбцы
  Oracle типа TIMESTAMP WITH LOCAL TIME ZONE и хотите представлять их
  в PostgreSQL как `timestamp without time zone`.

  Заметьте, что если вы измените `timezone` после установления подключения
  к Oracle, oracle_fdw не изменит часовой пояс сеанса Oracle.  В этом
  случае можно вызвать `oracle_close_connections()`, чтобы при следующем
  обращении к внешней таблице открылось новое подключение.

  Если Oracle не распознает часовой пояс, подключения будут завершаться
  ошибкой вида

      ORA-01882: timezone region not found

  В таком случае либо используйте другой `timezone`, либо оставьте
  параметр выключенным (`off`) и задайте подходящее значение переменной
  окружения ORA_SDTZ в окружении сервера PostgreSQL.

Параметры сопоставления пользователей
-------------------------------------

- **user** (обязательный)

  Имя пользователя Oracle для сеанса.  
  Для *внешней аутентификации* задайте пустую строку, если не хотите
  хранить учётные данные Oracle в базе PostgreSQL (один из простых
  способов — использовать *внешнее хранилище паролей*).

- **password** (обязательный)

  Пароль пользователя Oracle.

Параметры внешней таблицы
-------------------------

- **table** (обязательный)

  Имя таблицы Oracle.  Оно должно быть записано точно так, как оно
  встречается в системном каталоге Oracle, то есть как правило состоять
  только из символов верхнего регистра.

  Чтобы определить внешнюю таблицу на основе произвольного запроса Oracle,
  задайте этот параметр равным запросу, заключённому в круглые скобки,
  например

      OPTIONS (table '(SELECT col FROM tab WHERE val = ''string'')')

  В этом случае не задавайте параметр **schema**.  
  INSERT, UPDATE и DELETE работают и для внешних таблиц, определённых
  на простых запросах; если хотите этого избежать (или запутанных
  сообщений об ошибках Oracle для более сложных запросов), используйте
  параметр таблицы **readonly**.

- **dblink** (необязательный)

  Oracle database link, через который осуществляется доступ к таблице.
  Имя должно быть записано точно так, как оно встречается в системном
  каталоге Oracle, то есть как правило состоять только из символов
  верхнего регистра.

- **schema** (необязательный)

  Схема (владелец) таблицы.  Полезно для доступа к таблицам, которые не
  принадлежат подключающемуся пользователю Oracle.  Имя должно быть
  записано точно так, как оно встречается в системном каталоге Oracle,
  то есть как правило состоять только из символов верхнего регистра.

- **max_long** (необязательный, по умолчанию "32767")

  Максимальная длина любого столбца LONG, LONG RAW и XMLTYPE в таблице
  Oracle.  Возможные значения — целые числа от 1 до 1073741823
  (максимальный размер `bytea` в PostgreSQL).  Такой объём памяти будет
  выделен как минимум дважды, поэтому большие значения потребуют много
  памяти.  
  Если **max_long** меньше длины самого длинного полученного значения,
  вы получите сообщение об ошибке `ORA-01406: fetched column value was
  truncated`.

- **readonly** (необязательный, по умолчанию "false")

  INSERT, UPDATE и DELETE разрешены только для таблиц, у которых этот
  параметр не установлен в yes/on/true.

- **sample_percent** (необязательный, по умолчанию "100")

  Этот параметр влияет только на обработку ANALYZE и может быть полезен,
  чтобы выполнить ANALYZE очень больших таблиц за разумное время.

  Значение должно быть от 0.000001 до 100 и задаёт процент блоков таблицы
  Oracle, случайно выбираемых для вычисления статистики таблицы
  PostgreSQL.  Для этого используется предложение `SAMPLE BLOCK (x)`
  в Oracle.

  ANALYZE завершится ошибкой ORA-00933 для таблиц, определённых запросами
  Oracle, и может завершиться ошибкой ORA-01446 для таблиц, определённых
  сложными представлениями Oracle.

- **prefetch** (необязательный, по умолчанию "50")

  Задаёт число строк, получаемых за один обмен между PostgreSQL и Oracle
  при сканировании внешней таблицы.  Значение должно быть от 1 до 10240.

  Большие значения могут ускорить работу, но потребуют больше памяти
  на сервере PostgreSQL и могут привести к ошибкам нехватки памяти.
  Большие значения обычно не дают выгоды, если только строки таблицы
  не очень малы.  Будьте осторожны с большими значениями; вас
  предупредили.

  Заметьте, что упреждающая выборка не выполняется, если таблица Oracle
  содержит столбцы типа `MDSYS.SDO_GEOMETRY`.

- **lob_prefetch** (необязательный, по умолчанию "1048576")

  Задаёт число байтов, упреждающе выбираемых для значений BLOB, CLOB
  и BFILE.  Для LOB большего размера потребуются дополнительные обмены
  между PostgreSQL и Oracle, поэтому значение больше типичного размера
  ваших LOB улучшит производительность.  Большие значения этого параметра
  могут выделять больше памяти на стороне сервера, но повышают
  производительность для больших LOB.

Параметры столбцов
------------------

- **key** (необязательный, по умолчанию "false")

  Если задан yes/on/true, соответствующий столбец внешней таблицы Oracle
  считается столбцом первичного ключа.  
  Чтобы работали UPDATE и DELETE, этот параметр должен быть установлен
  для всех столбцов, входящих в первичный ключ таблицы.

- **strip_zeros** (необязательный, по умолчанию "false")

  Если задан yes/on/true, символы ASCII 0 будут удаляться из строки при
  передаче.  Такие символы допустимы в Oracle, но не в PostgreSQL, поэтому
  при чтении через oracle_fdw они вызовут ошибку.  Параметр имеет смысл
  только для столбцов `character`, `character varying` и `text`.

4 Использование
===============

Права в Oracle
--------------

Пользователю Oracle, очевидно, потребуются право CREATE SESSION и право
читать соответствующую таблицу или представление.  Заметьте, что oracle_fdw
обращается к таблице Oracle во время планирования запроса, чтобы получить
её определение.  Это происходит *до* проверки прав на внешнюю таблицу.
Как следствие, при обращении к внешней таблице, на которую у вас нет прав
в PostgreSQL, вы можете получить ошибку Oracle.  Это ожидаемо и не является
проблемой безопасности.

Для EXPLAIN VERBOSE пользователю также потребуются права SELECT на
V$SQL и V$SQL_PLAN.

Соединения
----------

oracle_fdw кэширует подключения к Oracle, поскольку создание сеанса Oracle
для каждого отдельного запроса — дорогая операция.  Все подключения
автоматически закрываются при завершении сеанса PostgreSQL.

Функция `oracle_close_connections()` позволяет закрыть все кэшированные
подключения к Oracle.  Это может быть полезно для долго живущих сеансов,
которые не обращаются к внешним таблицам постоянно и хотят не удерживать
ресурсы, нужные для открытого подключения Oracle.  
Вызывать эту функцию внутри транзакции, изменяющей данные Oracle, нельзя.

Столбцы
-------

При определении внешней таблицы столбцы таблицы Oracle отображаются
на столбцы PostgreSQL в порядке их определения.

oracle_fdw включает в запрос к Oracle только те столбцы, которые реально
нужны запросу PostgreSQL.

Таблица PostgreSQL может содержать больше или меньше столбцов, чем таблица
Oracle.  Если столбцов больше и они используются, вы получите
предупреждение, а значения будут NULL.

Если вы хотите выполнять UPDATE или DELETE, убедитесь, что параметр `key`
установлен для всех столбцов, входящих в первичный ключ таблицы.
Иначе будут ошибки.

Типы данных
------------

Столбцы PostgreSQL нужно определить с типами данных, которые oracle_fdw
умеет преобразовывать (см. таблицу преобразований ниже).  Это ограничение
проверяется, только если столбец реально используется, поэтому можно
определить «фиктивные» столбцы для непреобразуемых типов данных, лишь бы
вы к ним не обращались (этот трюк работает только с SELECT, но не при
изменении внешних данных).  Если значение Oracle превышает размер столбца
PostgreSQL (например, длину столбца varchar или максимальное целое
значение), вы получите ошибку во время выполнения.

oracle_fdw автоматически выполняет следующие преобразования:

    Тип Oracle               | Возможные типы PostgreSQL
    -------------------------+--------------------------------------------------
    CHAR                     | char, varchar, text
    NCHAR                    | char, varchar, text
    VARCHAR                  | char, varchar, text
    VARCHAR2                 | char, varchar, text, json
    NVARCHAR2                | char, varchar, text
    CLOB                     | char, varchar, text, json
    NCLOB                    | char, varchar, text, json
    LONG                     | char, varchar, text
    RAW                      | uuid, bytea
    BLOB                     | bytea
    BFILE                    | bytea (только чтение)
    LONG RAW                 | bytea
    NUMBER                   | numeric, float4, float8, char, varchar, text
    NUMBER(n,m) при m<=0     | numeric, float4, float8, int2, int4, int8,
                             |    boolean, char, varchar, text
    FLOAT                    | numeric, float4, float8, char, varchar, text
    BINARY_FLOAT             | numeric, float4, float8, char, varchar, text
    BINARY_DOUBLE            | numeric, float4, float8, char, varchar, text
    DATE                     | date, timestamp, timestamptz, char, varchar, text
    TIMESTAMP                | date, timestamp, timestamptz, char, varchar, text
    TIMESTAMP WITH TIME ZONE | date, timestamp, timestamptz, char, varchar, text
    TIMESTAMP WITH           | date, timestamp, timestamptz, char, varchar, text
       LOCAL TIME ZONE       |
    INTERVAL YEAR TO MONTH   | interval, char, varchar, text
    INTERVAL DAY TO SECOND   | interval, char, varchar, text
    XMLTYPE                  | xml, char, varchar, text
    MDSYS.SDO_GEOMETRY       | geometry (см. «Поддержка PostGIS» ниже)

При преобразовании NUMBER в boolean значение 0 означает `false`,
а любое другое значение — `true`.

Вставка или изменение XMLTYPE работает только со значениями, не
превышающими максимальную длину типа VARCHAR2 (4000 или 32767 в
зависимости от параметра `MAX_STRING_SIZE`).

Если хотите преобразовывать TIMESTAMP WITH LOCAL TIME ZONE в `timestamp`,
рассмотрите параметр `set_timezone` внешнего сервера.

Если нужны преобразования помимо перечисленных, определите подходящее
представление в Oracle или PostgreSQL.

Условия WHERE и предложения ORDER BY
------------------------------------

PostgreSQL использует все применимые части предложения WHERE как фильтр
при сканировании.  Запрос к Oracle, который строит oracle_fdw, будет
содержать предложение WHERE, соответствующее этим условиям, всякий раз,
когда такое условие можно безопасно перевести в SQL Oracle.  Эта
возможность, известная как *проталкивание предложений WHERE*, может сильно
уменьшить число строк, получаемых из Oracle, и позволит оптимизатору Oracle
выбрать хороший план доступа к нужным таблицам.

Аналогично предложения ORDER BY проталкиваются в Oracle, где это возможно.
Заметьте, что условия сортировки по символьной строке не проталкиваются,
поскольку порядок сортировки в PostgreSQL и Oracle нельзя гарантировать
одинаковым.

Чтобы воспользоваться этим, старайтесь использовать простые условия для
внешней таблицы.  Выбирайте типы данных столбцов PostgreSQL,
соответствующие типам Oracle, иначе условия нельзя будет перевести.

Выражения `now()`, `transaction_timestamp()`, `current_timestamp`,
`current_date` и `localtimestamp` переводятся корректно.

Вывод EXPLAIN покажет использованный запрос к Oracle, так что вы увидите,
какие условия были переведены в Oracle и как.

Соединения внешних таблиц
-------------------------

Начиная с PostgreSQL 9.6, oracle_fdw может проталкивать соединения на
сервер Oracle: соединение двух внешних таблиц приведёт к одному запросу
к Oracle, выполняющему соединение на стороне Oracle.

Есть несколько ограничений, при которых это возможно:

- Обе таблицы должны быть определены на одном внешнем сервере.
- Соединения трёх и более таблиц не проталкиваются.
- Соединение должно находиться в операторе SELECT.
- oracle_fdw должен суметь протолкнуть все условия соединения и
  предложения WHERE.
- Перекрёстные соединения без условий соединения не проталкиваются.
- Если соединение протолкнуто, предложения ORDER BY не проталкиваются.

Важно, чтобы статистика обеих внешних таблиц была собрана командой
ANALYZE, чтобы PostgreSQL мог выбрать лучшую стратегию соединения.

Изменение внешних данных
------------------------

oracle_fdw поддерживает INSERT, UPDATE и DELETE для внешних таблиц.
По умолчанию это разрешено (в том числе в базах данных, обновлённых
с ранних версий PostgreSQL) и может быть запрещено параметром таблицы
**readonly**.

Чтобы работали UPDATE и DELETE, столбцы, соответствующие столбцам
первичного ключа таблицы Oracle, должны иметь параметр столбца **key**.
Эти столбцы используются для идентификации строки внешней таблицы,
поэтому убедитесь, что параметр установлен для *всех* столбцов, входящих
в первичный ключ.

Если при INSERT вы опустите столбец внешней таблицы, ему будет присвоено
значение из предложения DEFAULT внешней таблицы PostgreSQL (или NULL,
если предложения DEFAULT нет).  Предложения DEFAULT соответствующих
столбцов Oracle не используются.
Если внешняя таблица PostgreSQL содержит не все столбцы таблицы Oracle,
для столбцов, не включённых в определение внешней таблицы, будут
использованы предложения DEFAULT Oracle.

Предложение RETURNING в INSERT, UPDATE и DELETE поддерживается, кроме
столбцов с типами Oracle LONG и LONG RAW (Oracle не поддерживает эти типы
в предложении RETURNING).

Триггеры на внешних таблицах поддерживаются начиная с PostgreSQL 9.4.
Для триггеров AFTER и FOR EACH ROW внешняя таблица не должна содержать
столбцов с типами Oracle LONG или LONG RAW, потому что такие триггеры
используют упомянутое предложение RETURNING.

Хотя изменение внешних данных работает, производительность не особенно
хороша, особенно при изменении многих строк, поскольку (в силу устройства
обёрток сторонних данных) каждая строка обрабатывается индивидуально.

Транзакции передаются в Oracle, поэтому BEGIN, COMMIT, ROLLBACK и
SAVEPOINT работают как ожидается.  Подготовленные операторы с участием
Oracle не поддерживаются.  Подробнее см. раздел
[Внутреннее устройство](#7-внутреннее-устройство).

Поскольку oracle_fdw по умолчанию использует сериализуемые транзакции,
операторы изменения данных могут привести к ошибке сериализации:

    ORA-08177: can't serialize access for this transaction

Это может произойти, если параллельные транзакции изменяют таблицу, и
вероятнее в долгих транзакциях.  Такие ошибки можно опознать по SQLSTATE
(40001).  Приложению, использующему oracle_fdw, следует повторять
транзакции, завершившиеся этой ошибкой.

Можно использовать другой уровень изоляции транзакций; см. обсуждение
в разделе [Параметры внешнего сервера](#параметры-внешнего-сервера).

EXPLAIN
-------

EXPLAIN в PostgreSQL покажет запрос, реально отправленный в Oracle.
EXPLAIN VERBOSE покажет план выполнения Oracle (это не работает с сервером
Oracle 9i и старше, см. [Проблемы](#8-проблемы)).

ANALYZE
-------

Анализ внешней таблицы командой ANALYZE для сбора статистики поддерживается
oracle_fdw.

Без статистики PostgreSQL не может оценить число строк в запросах
к внешней таблице, что может привести к выбору плохих планов выполнения.

PostgreSQL *не* собирает статистику по внешним таблицам автоматически
с помощью демона autovacuum, как для обычных таблиц, поэтому особенно
важно выполнять ANALYZE по внешним таблицам после создания и всякий раз,
когда удалённая таблица существенно изменилась.

Учтите, что анализ внешней таблицы Oracle приведёт к полному
последовательному сканированию таблицы.  Ускорить его можно параметром
таблицы **sample_percent**, использующим только выборку из таблицы Oracle.

Поддержка PostGIS
-----------------

Тип данных `geometry` доступен, только если установлен PostGIS.

Поддерживаются только типы геометрии POINT, LINE, POLYGON, MULTIPOINT,
MULTILINE и MULTIPOLYGON в двух и трёх измерениях.  Пустые геометрии
PostGIS не поддерживаются, потому что в Oracle Spatial им нет эквивалента.

Значения NULL для SRID Oracle преобразуются в 0 и наоборот.  Для других
преобразований между SRID Oracle и SRID PostGIS создайте файл `srid.map`
в каталоге `share` PostgreSQL.  Каждая строка этого файла должна содержать
SRID Oracle и соответствующий SRID PostGIS, разделённые пробельными
символами.  Для хорошей производительности держите файл небольшим.

Поддержка IMPORT FOREIGN SCHEMA
-------------------------------

Начиная с PostgreSQL 9.5 поддерживается IMPORT FOREIGN SCHEMA для массового
импорта определений всех таблиц схемы Oracle.  
В дополнение к документации IMPORT FOREIGN SCHEMA учтите следующее:

- IMPORT FOREIGN SCHEMA создаёт внешние таблицы для всех объектов,
  найденных в ALL_TAB_COLUMNS.  Это таблицы, представления и
  материализованные представления, но не синонимы.

- Это поддерживаемые параметры IMPORT FOREIGN SCHEMA:

  - **case**: управляет преобразованием регистра имён таблиц и столбцов
    при импорте

    Возможные значения:
    - `keep`: оставить имена как в Oracle, обычно в верхнем регистре.
    - `lower`: перевести все имена таблиц и столбцов в нижний регистр.
    - `smart`: переводить только имена, полностью состоящие из символов
               верхнего регистра в Oracle (это значение по умолчанию).

  - **collation**: правила сортировки, используемые для преобразования
    регистра параметрами `lower` и `smart` параметра **case**

    Значение по умолчанию — `default`, то есть правила сортировки базы
    данных по умолчанию.  Поддерживаются только правила сортировки из
    схемы `pg_catalog`.  Список возможных значений см. в столбце
    `collname` каталога `pg_collation`.

  - **dblink**: Oracle database link, через который осуществляется доступ
    к схеме

    Имя должно быть записано точно так, как оно встречается в системном
    каталоге Oracle, то есть как правило состоять только из символов
    верхнего регистра.

  - **readonly**: задаёт параметр **readonly** всем импортируемым таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

  - **skip_tables** (по умолчанию `false`): не импортировать таблицы

  - **skip_views** (по умолчанию `false`): не импортировать представления

  - **skip_matviews** (по умолчанию `false`): не импортировать
    материализованные представления

  - **max_long**: задаёт параметр **max_long** всем импортируемым таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

  - **sample_percent**: задаёт параметр **sample_percent** всем
    импортируемым таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

  - **prefetch**: задаёт параметр **prefetch** всем импортируемым таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

  - **lob_prefetch**: задаёт параметр **lob_prefetch** всем импортируемым
    таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

  - **nchar**: задаёт параметр **nchar** всем импортируемым таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

  - **set_timezone**: задаёт параметр **set_timezone** всем импортируемым
    таблицам

    Подробнее см. раздел [Параметры](#3-параметры).

- Имя схемы Oracle должно быть записано точно так, как в Oracle, то есть
  как правило в верхнем регистре.  Поскольку PostgreSQL переводит имена
  в нижний регистр перед обработкой, имя схемы нужно защитить двойными
  кавычками (например, `"SCOTT"`).

- Имена таблиц в предложениях LIMIT TO или EXCEPT должны быть записаны
  так, как они будут выглядеть в PostgreSQL после описанного выше
  преобразования регистра.

Заметьте, что IMPORT FOREIGN SCHEMA не работает с сервером Oracle 8i;
подробнее см. раздел [Проблемы](#8-проблемы).

5 Требования к установке
========================

oracle_fdw должен компилироваться и работать на любой платформе,
поддерживаемой PostgreSQL и клиентом Oracle, хотя проверить это я мог
только на Linux и Windows.

Требуется PostgreSQL версии 15 или новее.
PostgreSQL 14 и старше не поддерживаются: поддержка PostgreSQL 14
прекратилась в ноябре 2026 года, тогда как PostgreSQL 15 поддерживается
до ноября 2027 года.

Из-за нарушений API в минорных выпусках PostgreSQL следующие версии
использовать нельзя:

- 15.0–15.1

Как всегда, для любой используемой версии PostgreSQL следует устанавливать
последний минорный выпуск.

oracle_fdw написан для стандартного открытого PostgreSQL.
Ответвления PostgreSQL, такие как «PostgresPro» и «Postgres-XL», скорее
всего, несовместимы.
Если вы всё же хотите попробовать, придётся собрать oracle_fdw из исходных
текстов.
Если возникнут проблемы с таким сервером на основе PostgreSQL, прежде чем
сообщать о них, попробуйте с оригинальной версией.

Требуется клиент Oracle версии 11.2 или новее.
Заметьте, что матрица регрессионных тестов покрывает только клиенты Oracle 19
и 23 и серверы Oracle 18, 21 и 23; Oracle 11.2 остаётся документированной
нижней границей как унаследованное обязательство от upstream oracle_fdw, но
тестами здесь не покрывается.
oracle_fdw можно собрать и использовать как с Oracle Instant Client, так
и с клиентом и сервером Oracle, установленными через Universal Installer.
Двоичные файлы, собранные с клиентом Oracle 11, можно использовать
с более поздними версиями клиента без перекомпиляции и пересборки связей.

Поддерживаемые версии сервера Oracle зависят от используемой версии
клиента (см. матрицу совместимости Oracle Client/Server в документе
Oracle Support 207303.1).  У PostgreSQL и Oracle должна быть одинаковая
архитектура.
Например, нельзя, чтобы у одного было 32-разрядное программное обеспечение,
а у другого 64-разрядное.

Рекомендуется использовать последний набор исправлений (Patch Set) и на
клиенте Oracle, и на сервере, особенно для версий Oracle, снятых
с поддержки.  
Список известных ошибок Oracle, влияющих на работу oracle_fdw, см. в
разделе [Проблемы](#8-проблемы).  
Советы по установке и настройке Oracle ищите в Wiki oracle_fdw
(https://github.com/laurenz/oracle_fdw/wiki) и делитесь там собственными
знаниями.

6 Установка
===========

Если вы используете двоичный дистрибутив oracle_fdw, перейдите сразу
к разделу «Установка расширения» ниже.  Дополнительные подсказки по
установке oracle_fdw можно найти в
[Wiki](https://github.com/laurenz/oracle_fdw/wiki).

Сборка oracle_fdw на платформах, отличных от Windows:
-----------------------------------------------------

oracle_fdw написан как расширение PostgreSQL и на всех платформах, кроме
Windows, использует инфраструктуру сборки расширений PGXS.  Установка
должна быть простой.  О сборке в Windows см. следующий раздел.

Потребуются установленные заголовочные файлы PostgreSQL и PGXS.  Если
PostgreSQL установлен из двоичных пакетов, установите пакет «development».
Убедитесь, что установлены все системные пакеты, которые требовались для
сборки PostgreSQL (в системах на базе Redhat это может быть
«redhat-rpm-config»).

Также нужно установить заголовочные файлы C от Oracle (пакет SDK для
Instant Client).  Если вы используете ZIP-файлы Instant Client от Oracle,
возможно, вам придётся самому создать символическую ссылку с
`libclntsh.so` на фактический файл разделяемой библиотеки (обычно это
делает пакет SDK).

Убедитесь, что PostgreSQL сконфигурирован с `--without-ldap` (как минимум
сервер).  См. раздел [Проблемы](#8-проблемы).

Убедитесь, что `pg_config` есть в PATH (проверьте командой
`pg_config --pgxs`).  
Установите переменную окружения ORACLE_HOME равной каталогу установки
Oracle.

Распакуйте исходный код oracle_fdw и перейдите в этот каталог.  
Тогда установка должна быть такой же простой, как:

    $ make
    $ make install

Для второго шага нужны права записи в каталоги, где установлен PostgreSQL.

Если хотите собрать oracle_fdw внутри дерева исходных текстов PostgreSQL,
используйте

    $ make NO_PGXS=1

Сборка oracle_fdw в Windows:
----------------------------

Для сборки oracle_fdw в Windows потребуются:

- Заголовочные файлы и библиотеки PostgreSQL. Их можно найти в каталоге
  установки PostgreSQL.
- Заголовочные файлы и библиотеки Oracle (пакет SDK для Instant Client).
- Microsoft Visual Studio 2013 или новее.

Для сборки либо откройте `oracle_fdw\msvc\oracle_fdw.sln` в IDE, либо:

- Откройте командную строку разработчика (x86 или x64 в зависимости от
  вашей установки PostgreSQL) и перейдите в каталог `oracle_fdw\msvc`.
- Выполните (одной командной строкой):

      > msbuild oracle_fdw.sln /p:Configuration=(Debug or Release) ^
            /p:Platform=(Win32 or x64) ^
            /p:OracleClient=(path to Oracle Client/SDK) ^
            /p:PostgreSQL=(path to PostgreSQL installation)

  («^» — это продолжения строки; вместо этого можно написать всё
  в одной строке.)

Когда сборка завершится, вы найдёте `oracle_fdw.dll` в подкаталоге,
названном по параметрам сборки, например `x64\Release`.

Если вы используете Visual Studio 2015 или новее и получаете ошибки
о отсутствующих заголовочных файлах, включая `sys/types.h`, установите
Universal CRT SDK (он входит в Visual Studio).

Скопируйте `oracle_fdw.dll` в каталог библиотек PostgreSQL, а
`oracle_fdw.control` и SQL-файлы — в подкаталог `extension` каталога share
PostgreSQL.  
Найти эти каталоги можно командами `pg_config --libdir` и
`pg_config --sharedir`.

Установка расширения:
---------------------

Убедитесь, что разделяемая библиотека oracle_fdw установлена в каталоге
библиотек PostgreSQL, а `oracle_fdw.control` и SQL-файлы — в каталоге
расширений PostgreSQL.

Поскольку разделяемая библиотека клиента Oracle, скорее всего, не входит
в стандартный путь поиска библиотек, нужно сделать так, чтобы сервер
PostgreSQL мог её найти.  Способ зависит от операционной системы; в Linux
можно задать LD_LIBRARY_PATH или использовать `/etc/ld.so.conf`.

Убедитесь, что все необходимые переменные окружения Oracle установлены
в окружении процесса сервера PostgreSQL (ORACLE_HOME, если вы не
используете Instant Client, TNS_ADMIN, если у вас есть файлы конфигурации,
и т. п.)

Чтобы установить расширение в базе данных, подключитесь как
суперпользователь и выполните

    CREATE EXTENSION oracle_fdw;

Это определит необходимые функции и создаст обёртку сторонних данных.

Чтобы обновиться с версии oracle_fdw до 2.3.0, выполните

    ALTER EXTENSION oracle_fdw UPDATE;

Заметьте, что версия расширения, которую показывает команда psql `\dx`
или системный каталог `pg_available_extensions`, — это *не* установленная
версия oracle_fdw.  Чтобы узнать версию oracle_fdw, используйте функцию
`oracle_diag`.

Запуск регрессионных тестов:
----------------------------

Если вы не разрабатываете oracle_fdw и не хотите проверить его работу
на экзотической платформе, делать это не нужно.

Чтобы регрессионные тесты работали, у вас должен быть запущен кластер
PostgreSQL и сервер Oracle (10.2 или новее с Locator или Spatial), а
двоичные файлы oracle_fdw должны быть установлены.  
Регрессионные тесты создадут базу данных с именем `contrib_regression`
и выполнят ряд тестов.  Чтобы успешно прошли регрессионные тесты PostGIS,
должны быть установлены двоичные файлы PostGIS.

База данных Oracle должна быть подготовлена так:
- Должен существовать пользователь `scott` с паролем `tiger` (если только
  вы не хотите править скрипты регрессионных тестов).  Пользователю нужны
  системные привилегии CREATE SESSION, CREATE TABLE, CREATE VIEW и
  CREATE MATERIALIZED VIEW, достаточная квота в табличном пространстве
  по умолчанию, а также права SELECT на V$SQL и V$SQL_PLAN.

Настройте окружение сервера PostgreSQL так, чтобы он мог устанавливать
подключение к Oracle без строки подключения:
Если сервер Oracle находится на той же машине, задайте соответствующие
переменные окружения ORACLE_SID и ORACLE_HOME; для удалённого сервера
задайте переменную окружения TWO_TASK (или LOCAL в Windows) равной строке
подключения.

Регрессионные тесты запускаются так:

    $ make installcheck

Регрессионные тесты поддерживаются в актуальном состоянии с последней
разрабатываемой версией PostgreSQL.  При запуске с более старыми версиями
PostgreSQL возможны небольшие различия, например изменённые сообщения
об ошибках или другой формат вывода psql.

7 Внутреннее устройство
=======================

oracle_fdw задаёт MODULE сеанса Oracle равным `postgres`, а ACTION —
номеру процесса-бэкенда.  Это помогает идентифицировать сеанс Oracle
и позволяет трассировать его с помощью
DBMS_MONITOR.SERV_MOD_ACT_TRACE_ENABLE.

oracle_fdw использует интерфейс массивов Oracle, чтобы избежать лишних
обменов клиент—сервер.  Размер пакета можно настроить параметром таблицы
**prefetch**; по умолчанию он равен 50.

Вместо использования PLAN_TABLE для объяснения запроса к Oracle (что
потребовало бы создания такой таблицы в базе Oracle) oracle_fdw использует
планы выполнения, хранящиеся в кэше библиотек.  Для этого запрос к Oracle
*явно описывается* (DESCRIBE), что заставляет Oracle разобрать запрос.
Сложность в том, чтобы найти SQL_ID и CHILD_NUMBER оператора в V$SQL,
поскольку столбец SQL_TEXT содержит только первые 1000 байтов запроса.
Поэтому oracle_fdw добавляет к запросу комментарий, содержащий хеш текста
запроса.  По нему выполняется поиск в V$SQL.
Сам план выполнения или сведения о стоимости извлекаются из V$SQL_PLAN.

oracle_fdw использует на стороне Oracle уровень изоляции транзакций
SERIALIZABLE, соответствующий REPEATABLE READ в PostgreSQL.  Это
необходимо, потому что один оператор PostgreSQL может привести
к нескольким запросам к Oracle (например, при соединении вложенным
циклом), и результаты должны быть согласованными.  
К сожалению, реализация SERIALIZABLE в Oracle имеет свои особенности;
подробнее см. раздел [Проблемы](#8-проблемы).

Транзакция Oracle фиксируется непосредственно перед фиксацией локальной
транзакции, так что завершённая транзакция PostgreSQL гарантирует
завершение транзакции Oracle.  Однако есть небольшая вероятность, что
транзакция PostgreSQL не сможет завершиться, хотя транзакция Oracle уже
зафиксирована.  Этого нельзя избежать без двухфазных транзакций и
менеджера транзакций, что выходит за рамки разумных возможностей обёртки
сторонних данных.  
Подготовленные операторы с участием Oracle по той же причине
не поддерживаются.

8 Проблемы
==========

Кодировки
---------

Символы, хранящиеся в базе Oracle, которые нельзя преобразовать в кодировку
базы PostgreSQL, будут молча заменены Oracle на *символы замены*,
как правило обычный или перевёрнутый вопросительный знак.
Вы не получите ни предупреждения, ни сообщения об ошибке.

Если вы используете кодировку базы PostgreSQL, которую Oracle не знает
(сейчас это EUC_CN, EUC_KR, LATIN10, MULE_INTERNAL, WIN874 и SQL_ASCII),
символы, отличные от ASCII, не смогут быть преобразованы правильно.
В этом случае вы получите предупреждение, а символы будут заменены
символами замены, как описано выше.

Можно задать параметр **nls_lang** обёртки сторонних данных, чтобы
принудительно использовать определённую кодировку Oracle, но полученные
символы, скорее всего, будут неверными и приведут к сообщениям об ошибках
PostgreSQL.  Вероятно, это имеет смысл только для кодировки SQL_ASCII,
если вы понимаете, что делаете.
См. раздел [Параметры](#3-параметры).

Ограниченная функциональность старых версий Oracle
--------------------------------------------------

- Определение системных каталогов Oracle V$SQL и V$SQL_PLAN изменилось
  в Oracle 10.1.  Использование EXPLAIN VERBOSE с более старыми версиями
  сервера Oracle приведёт к ошибкам вида:

      ERROR:  error describing query: OCIStmtExecute failed to execute
              remote query for sql_id
      DETAIL:  ORA-00904: "LAST_ACTIVE_TIME": invalid identifier

  Исправлять это не планируется, поскольку Oracle 9i с 2010 года вне
  расширенной поддержки, а эта функциональность не критична.

- IMPORT FOREIGN SCHEMA выдаёт следующую ошибку с сервером Oracle 8i:

      ERROR:  error importing foreign schema: OCIStmtExecute failed to execute
              column query
      DETAIL:  ORA-00904: invalid column name

  Это потому, что представлению ALL_TAB_COLUMNS не хватает столбца
  CHAR_LENGTH, добавленного в Oracle 9i.

Библиотеки LDAP
---------------

Разделяемая библиотека клиента Oracle поставляется с собственной
реализацией LDAP-клиента, соответствующей
[RFC 1823](http://www.rfc-base.org/rfc-1823.html), поэтому эти функции
имеют те же имена, что и функции OpenLDAP.  Это приведёт к конфликту имён,
если сервер PostgreSQL сконфигурирован с `--with-ldap`.

Конфликт имён не будет обнаружен, поскольку oracle_fdw загружается во время
выполнения, но проблемы возникнут, если кто-нибудь вызовет функцию LDAP.
Обычно первой загружается OpenLDAP, поэтому если Oracle вызовет функцию
LDAP (например, при использовании разрешения имён *directory naming*),
бэкенд аварийно завершится.  Это может привести к сообщениям вроде
следующего (наблюдавшегося в Linux) в журнале сервера PostgreSQL:

    ../../../libraries/libldap/getentry.c:29: ldap_first_entry:
     Assertion `( (ld)->ld_options.ldo_valid == 0x2 )' failed.

Лучшее решение — сконфигурировать PostgreSQL с `--without-ldap`.  Это
единственный надёжный способ избежать проблемы.  
Даже когда PostgreSQL собран с `--with-ldap`, всё может работать, пока вы
не используете никакую клиентскую функциональность LDAP в Oracle.  
На некоторых платформах можно принудительно загрузить разделяемую
библиотеку клиента Oracle до запуска сервера PostgreSQL (LD_PRELOAD
в Linux).  Тогда должны использоваться функции LDAP от Oracle.  В этом
случае Oracle, возможно, сможет пользоваться LDAP, но использование LDAP
из PostgreSQL будет приводить к падению бэкенда.

Использовать функциональность LDAP одновременно в PostgreSQL и в Oracle
нельзя, точка.

Ошибки сериализации
-------------------

В Oracle 11.2 и новее вставка первой строки в только что созданную таблицу
Oracle через oracle_fdw приведёт к ошибке сериализации.

Это связано с возможностью Oracle *отложенного создания сегментов*
(deferred segment creation), которая откладывает выделение места для новой
таблицы до вставки первой строки.  Из-за этого возникает ошибка
сериализации с сериализуемыми транзакциями (см. документ 1285464.1
в базе знаний Oracle).

Это не серьёзная проблема; можно обойти её, либо игнорируя первую ошибку,
либо создавая таблицу с SEGMENT CREATION IMMEDIATE.

Куда более неприятная проблема — параллельные вставки иногда вызывают
ошибки сериализации, когда страница индекса расщепляется параллельно
с изменяющей сериализуемой транзакцией (см. документ Oracle 160593.1).

Oracle утверждает, что это не ошибка, и предлагает повторить транзакцию,
получившую ошибку сериализации.

Ошибки Oracle
-------------

Это список ошибок Oracle, которые влияли или влияют на oracle_fdw.

Баг 2728408 может вызывать `ORA-8177 cannot serialize access for this
transaction` даже без попытки изменения удалённых данных.  
Он может проявляться на сервере Oracle 8.1.7.4 (установите единичный патч
2728408) или Oracle 9.2 (установите Patch Set 9.2.0.4 или новее).

Известно, что клиент Oracle 21c не работает со столбцами CLOB (они
выглядят пустыми).  Окончательного доказательства, что это баг Oracle,
нет, но другие версии работают нормально.

Отсутствует клиентская DLL Oracle (только в Windows)
----------------------------------------------------

Следующее сообщение об ошибке (из любого запроса с участием внешней
таблицы Oracle) означает, что PostgreSQL не может найти клиентскую
библиотеку Oracle:

    ERROR:  Oracle client library (oci.dll) not found
    DETAIL:  No Oracle client is installed, or your system is configured incorrectly.
    HINT:  Verify that the PATH variable includes the Oracle client.

Убедитесь, что путь к `oci.dll` включён в переменную окружения PATH
пользователя, от имени которого работает сервер PostgreSQL.  Если он
работает как служба Windows, это системное окружение, и после его
изменения службу нужно перезапустить.

Если обновление окружения не помогает, возможно, вы используете
дистрибутив PostgreSQL со своими переменными окружения, которые скрывают
клиент Oracle.  Подробнее см. сообщение об ошибке на
https://github.com/laurenz/oracle_fdw/issues/160.

9 Поддержка
===========

Загляните в [Wiki](https://github.com/laurenz/oracle_fdw/wiki) за помощью
по настройке на определённых платформах и по другим проблемам.
Также может помочь поиск в
[GitHub issues](https://github.com/laurenz/oracle_fdw/issues) — возможно,
вы не первый, кто столкнулся с этой проблемой.

Если хотите сообщить о проблеме с oracle_fdw, и имя внешнего сервера,
например, «ora_serv», включите в отчёт вывод

    SELECT oracle_diag('ora_serv');

Если это вызывает ошибку, включите также вывод

    SELECT oracle_diag();

Если у вас проблема или вопрос или любой другой отзыв, предпочтительный
вариант — открыть issue на GitHub:  
https://github.com/laurenz/oracle_fdw/issues  
Для этого нужна учётная запись GitHub.

Коммерческая поддержка доступна от
[CYBERTEC PostgreSQL International GmbH](https://www.cybertec-postgresql.com).
